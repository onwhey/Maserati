# 领域信号实现逻辑复核清单

## 1. 复核目的

本文件用于约束“领域信号复核”这件事本身。

复核领域信号的目的不是调页面展示，也不是为了让某一段回测结果更好看，而是重新检查六个领域层的真实实现逻辑是否合理：

```text
Feature 怎么算；
AtomicSignal 怎么判断；
DomainSignal 怎么聚合；
最终领域结论怎么表达；
这个领域事实是否被过度命名、过度解释或越权使用。
```

复核结论分三类：

```text
合理：保持现状；
局部不合理：按问题所在层级修改 Feature / AtomicSignal / DomainSignal；
整体口径不合理：先补需求文档，再重新设计该领域版本。
```

## 2. 复核范围

当前必须复核六个正式领域：

| 领域 | 复核重点 |
|---|---|
| market_context | 大级别市场背景是否只是描述背景，是否过度决定方向 |
| trend | 趋势方向、趋势强度、1d 与 4h 的关系是否合理 |
| momentum | 动能强弱、衰竭、增强、震荡是否被正确区分 |
| volatility | 波动状态是否只描述波动，不越权解释方向或交易动作 |
| structure | 支撑、压力、区间、位置、破位、突破是否定义合理 |
| risk_state | 风险状态是否只描述信号可靠性风险，不替代风控或交易决策 |

## 3. 复核原则

### 3.1 不预设修改层级

发现问题后，不默认只改 DomainSignal。

问题在哪一层，就改哪一层：

```text
Feature 算法不合理 → 改 Feature；
AtomicSignal 判断条件不合理 → 改 AtomicSignal；
DomainSignal 聚合逻辑不合理 → 改 DomainSignal；
字段命名或中文解释误导 → 改命名、说明和展示；
需求口径不清楚 → 先补需求文档。
```

### 3.2 不对着单个行情补规则

不得因为某一个日期、某一张图、某一次回测结果看起来别扭，就直接新增规则。

必须先判断它是：

```text
单个样本噪音；
某类行情的稳定问题；
算法定义本身的问题；
命名和展示误导的问题。
```

只有当问题能抽象成稳定规则，才进入修改。

### 3.3 领域层只描述市场事实

领域信号不得输出交易动作。

领域层可以说：

```text
趋势偏空；
动能衰竭；
波动极高；
结构压力有效；
市场背景深度回撤；
风险状态升高。
```

领域层不得说：

```text
应该做多；
应该做空；
应该减仓；
应该空仓；
应该追单；
应该暂停交易。
```

这些必须留给 MarketRegime、StrategyRouting、StrategySignal、DecisionSnapshot 或更下游模块在各自边界内处理。

## 4. 每个领域必须回答的问题

复核每个领域时，至少回答以下问题：

| 问题 | 说明 |
|---|---|
| 这个领域到底回答什么市场问题？ | 不能和其它领域重复 |
| 它依赖哪些 AtomicSignal？ | 区分必需原子和可选原子 |
| AtomicSignal 依赖哪些 Feature？ | 确认特征是否真的支撑该判断 |
| 当前结论是不是名字过重？ | 例如“支撑”是否其实只是“历史反应区” |
| 当前算法是不是过粗？ | 是否用过宽区间、过长窗口、过少条件得出强结论 |
| 是否存在主结论误导？ | 多个事实并存时，是否被压成单一结论 |
| 是否存在越权？ | 是否暗示交易动作、目标仓位或风控动作 |
| 是否能被人工复核？ | 页面和证据是否能解释“为什么这么判断” |

## 5. 复核输出格式

每个领域复核完成后，输出一份简短结论：

```text
领域：
当前结论：
是否保留：
发现的问题：
问题所在层级：
建议修改：
是否需要先补文档：
是否需要回测验证：
```

示例：

```text
领域：structure
当前结论：支撑/压力事实可计算，但旧支撑算法把宽价格聚类区当成支撑位。
是否保留：部分保留。
发现的问题：宽区间不能直接称为支撑位。
问题所在层级：Feature + AtomicSignal + DomainSignal 命名。
建议修改：新增基于有效局部低点/高点的支撑压力算法；旧宽区间降级为历史反应区。
是否需要先补文档：是。
是否需要回测验证：是。
```

## 6. 当前已知优先问题

### 6.1 Structure 支撑/压力算法

当前 1d 大支撑/压力算法存在明显问题：

```text
过宽价格聚类区被命名为支撑/压力；
例如 71,522 - 78,228 这种大约 9% 的区间，不应被称为明确支撑位；
它最多只能称为历史反应区。
```

新版支撑/压力算法优先级为 P0。

方向：

```text
支撑来自有效局部低点；
压力来自有效局部高点；
局部低点/高点必须满足反弹/回落幅度、时间间隔和当前确认条件；
宽价格聚类区降级为历史反应区，只作为可选或辅助证据。
```

### 6.2 六领域整体复核

Structure 暴露的问题说明：领域层可能存在“名字过重、算法过粗、主结论误导”的共性风险。

因此，不能只修 Structure，还需要逐个复核：

```text
market_context
trend
momentum
volatility
structure
risk_state
```

## 7. 本阶段不做什么

本阶段不直接：

```text
修改 MarketRegime；
修改 StrategyRouting；
修改 StrategyDefinition；
修改 DecisionSnapshot；
修改仓位算法；
新增交易动作；
为了某一段收益反推领域信号规则。
```

只有当领域事实复核完成，且确认 MarketRegime 消费领域事实存在问题时，才进入 MarketRegime 复核或修改。
## 待补充问题：成交量没有进入领域判断

当前系统已经采集 K 线成交量，并且 Feature 层存在基础成交量特征，例如最新 4h 成交量和 4h 均量。

但在六个领域信号中，成交量目前没有真正进入核心判断。尤其是 momentum 领域，当前推动力主要来自价格涨跌幅、加速度、连续性和收盘强弱，没有使用成交量确认。

复核 momentum 时必须单独判断：

```text
上涨推动是否需要成交量确认；
下跌推动是否需要成交量确认；
缩量上涨/缩量下跌是否应降低动能质量；
放量滞涨/放量滞跌是否应表达为分歧、吸收或派发候选；
成交量证据应放在 Feature、AtomicSignal 还是 DomainSignal 聚合层。
```

该问题先记录，不直接编码。后续如果进入修改，必须先补 momentum 相关需求文档，再实现 Feature / AtomicSignal / DomainSignal。
