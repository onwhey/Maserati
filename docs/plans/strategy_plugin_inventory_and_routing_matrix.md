# 策略插件库存与路由矩阵

## 1. 文档定位

本文档用于整理当前已经存在的策略插件、市场环境到策略插件的可配置关系，以及“保守 / 标准 / 进攻 / 混合”策略组合还缺哪些零件。

它不是策略算法需求文档，也不修改任何交易规则。

本文档只回答三件事：

```text
现在已经有哪些策略插件；
每种市场环境目前可以接到哪些策略；
如果要做保守、标准、进攻、混合四类策略组合，还缺什么。
```

本文档不负责：

```text
修改 MarketRegime 算法；
修改 StrategySignal 算法；
修改 DecisionSnapshot 仓位映射；
修改 OrderPlan 或真实交易链路；
根据回测结果自动优化参数；
自动上线策略；
真实下单。
```

## 2. 当前核心口径

### 2.1 三类对象的关系

```text
市场环境 = 客观行情事实
策略路由 = 后台人工配置的接线表
策略插件 = 真正表达交易方法论的算法零件
```

市场环境只回答“现在是什么行情”，例如：

```text
多头趋势延续；
空头趋势延续；
多头回调；
空头反弹；
高风险环境；
不明确环境。
```

策略路由只回答“这种行情交给哪个策略插件处理”。

策略插件才回答“我在这个行情里要不要交易、做多还是做空、信号强不强、价格条件是什么”。

所以，保守、标准、进攻不应该写死在 MarketRegime，也不应该写死成唯一的路由代码。它们应该通过后台把同一种市场环境接到不同的策略插件来表达。

### 2.2 一个版本包只能选择一个策略路由

策略路由本身已经是一整套接线表。一个版本包同时选择两个策略路由，会出现同一种市场环境被两套规则抢占的问题。

因此当前口径是：

```text
一个 StrategyAnalysisRelease 只能纳入一个 StrategyRouting。
这个 StrategyRouting 内部包含多条路由规则。
每条路由规则把一种市场环境接到一个策略插件版本。
```

### 3.1 目前明显缺失的插件

| 缺失策略插件 | 用途 | 是否影响当前标准组合 |
|---|---|---|
| 保守型多头趋势跟随 | 牛市或多头趋势里，只参与更确定的大级别顺势行情 | 不影响标准组合，但影响“纯保守组合” |
| 保守型空头趋势跟随 | 熊市或空头趋势里，只参与更确定的大级别顺势行情 | 不影响标准组合，但影响“纯保守组合” |
| 进攻型多头趋势跟随 | 多头环境下更快跟随短周期动能 | 不影响标准组合，但影响“纯进攻组合” |
| 进攻型空头趋势跟随 | 空头环境下更快跟随短周期动能 | 不影响标准组合，但影响“纯进攻组合” |
| 进攻型空头背景反弹做多 | 熊市或空头背景中，确认短周期反弹时参与多头反弹 | 标准组合不需要，但进攻组合需要 |
| 进攻型多头背景回调做空 | 牛市或多头背景中，确认短周期回调时参与短空 | 标准组合不需要，但进攻组合需要 |
| 区间震荡策略 | 无方向震荡中做区间支撑 / 压力 | 当前只有不交易策略，若要做区间交易则缺失 |
| 反转确认策略 | 顶部 / 底部反转从候选变为确认后参与 | 当前只有“未确认不交易”，若要做反转交易则缺失 |

## 5. 当前可直接拼出来的组合

### 5.1 标准趋势组合 v1

当前已经基本可拼。

逻辑是：

```text
多头延续 / 向上突破 → 多头趋势跟随
多头回调 / 多头高位震荡 → 多头回调支撑
空头延续 / 向下跌破 → 空头趋势跟随
空头反弹 / 空头低位震荡 → 空头反弹压制
顶部反转候选 / 底部反转候选 / 无方向震荡 / 高风险 / 不明确 → 显式不交易策略
```

这就是目前最完整的一套“标准趋势型”组合。

### 5.2 保守组合 v1

当前可以拼出“保守等待版”，但还不是完全独立的保守趋势系统。

如果允许暂时复用标准策略，那么可以拼出一个“偏保守组合”：

```text
明确趋势延续 → 复用标准趋势跟随
回调 / 反弹 / 高位震荡 / 低位震荡 / 反转候选 / 高风险 / 不明确 → 不交易
```

但这不是真正独立的保守策略，因为趋势延续部分仍然复用了标准趋势插件。

如果要做“趋势延续也更保守”的完整保守组合，还需要：

```text
保守型多头趋势跟随；
保守型空头趋势跟随。
```

### 5.3 进攻组合 v1

当前不能完整拼出来。

原因是进攻组合的核心不是“只把仓位调大”，而是策略方法论不同：

```text
熊市反弹确认时，可以考虑参与短周期多头；
牛市回调确认时，可以考虑参与短周期空头；
趋势延续时更快跟随短周期动能。
```

当前缺少这些 StrategyDefinition，因此不能只靠改路由完成真正进攻组合。

### 5.4 混合组合 v1

当前可以做一部分。

例如：

```text
多头环境使用标准多头策略；
空头环境使用保守空头策略；
震荡和高风险统一不交易。
```

但它的完整程度取决于保守 / 进攻插件是否补齐。

## 6. 下一步建议

### 6.1 先不要改仓位

当前阶段先判断：

```text
市场事实是否正确；
市场环境是否合理；
路由是否把环境交给了符合方法论的策略；
策略信号是否符合该策略的交易思路。
```

仓位映射后面单独处理。否则会把“策略判断问题”和“仓位大小问题”混在一起。

### 6.2 先补最小策略插件缺口

优先级建议：

1. 进攻型空头背景反弹做多；
2. 进攻型多头背景回调做空；
3. 保守型多头 / 空头趋势跟随；
4. 进攻型多头 / 空头趋势跟随；
5. 区间震荡策略；
6. 反转确认策略。

这样能最快验证三个问题：

```text
保守组合是否能减少震荡亏损；
进攻组合是否能更好捕捉反弹 / 回调；
混合组合是否能优于单一风格组合。
```

### 6.3 后台路由配置的验收标准

生成版本包后，必须能验证：

```text
版本包里只包含一个策略路由；
策略路由包含完整的市场环境覆盖规则；
每条路由规则绑定到明确的策略插件版本；
版本包里的策略插件只来自当前策略路由引用；
不存在策略路由没有引用、但被额外打包进去的策略；
回测每个周期都能进入某个策略插件，包括明确不交易策略；
不再出现“市场环境识别成功，但没有策略可选”的空洞。
```

## 7. 验收方式

本文档本身不写库、不访问外部服务、不触发交易。

后续做功能或登记策略时，验收应分三层：

```text
第一层：后台组件页能看清楚每个策略路由和它绑定的策略；
第二层：生成版本包后，数据库中版本包组件与路由绑定一致；
第三层：回测周期中每个市场环境都能落到一个策略插件，哪怕是不交易策略。
```

通过标准：

```text
不会因为某个市场环境没有策略而停在 StrategyRouting；
不会把未被当前策略路由引用的 StrategyDefinition 打进版本包；
可以分别生成标准、保守、进攻或混合版本包进行回测对比。
```

失败标准：

```text
同一个版本包选择了多个策略路由；
路由规则引用了不存在或未纳入版本包的策略插件；
版本包额外包含路由没有引用的策略插件；
某些市场环境只能输出“无策略”，而不是进入显式不交易策略；
回测时策略路由成功但后续 StrategySignal 无法生成。
```
